# Type-Safe User Strings Implementation Plan

**Issue:** #115
**Branch:** `feat/string-file`
**Goal:** Externalize all user-facing strings into a `.properties` file with compile-time safe access via generated constants.

## Architecture

### Source of truth
`src/main/resources/songscribe/strings.properties` — the only file developers maintain.

### Generated class
`target/generated-sources/songscribe/Strings.java` — generated by a Groovy script during the `generate-sources` Maven phase, registered via `build-helper-maven-plugin`. Not committed to git. Contains:

- A `public static final String` constant for every key in the properties file
- A `ResourceBundle` loaded at class init
- `get(String key)` — returns the localized string
- `get(String key, Object... args)` — returns the string formatted via `MessageFormat.format()`

### Build-time data flow

```
                    generate-sources phase
                    =====================
strings.properties ──> Groovy script ──> Strings.java
  (src/main/          (scripts/            (target/generated-sources/
   resources/)     generate-strings.groovy)  songscribe/)
                                               │
                    build-helper-maven-plugin   │
                    registers generated-sources │
                    as compile source root      │
                                               │
                    process-sources phase       │
                    ====================       │
                        Kotlin compile ◄───────┘
                                               │
                    compile phase              │
                    =============              │
                        Java compile ◄─────────┘
                                               │
                    runtime                    │
                    =======                    │
                        ResourceBundle ──> strings.properties
                                          (from classpath)
```

### Key naming convention

Properties keys use hierarchical dot-separated names. The constant name is derived by uppercasing and replacing dots with underscores.

| Properties key | Generated constant |
|---|---|
| `menu.file` | `MENU_FILE` |
| `action.export.pdf` | `ACTION_EXPORT_PDF` |
| `dialog.about.title` | `DIALOG_ABOUT_TITLE` |
| `error.file.open` | `ERROR_FILE_OPEN` |

### Key format rules

Keys must match the regex `[a-z][a-z0-9]*(\.[a-z][a-z0-9]*)*`:

- Lowercase letters and digits only (no hyphens, underscores, or uppercase)
- Segments separated by dots
- Each segment must start with a letter

The Groovy generator validates every key against this regex and fails the build with a clear error if any key is invalid.

### Key collision detection

The generator checks for collisions after converting keys to constant names. If two keys map to the same constant (e.g., this cannot happen with the strict key format above, but the check exists as a safety net), the build fails with an error naming both offending keys.

### Key hierarchy

Use these prefixes consistently:

| Prefix | Usage |
|---|---|
| `menu.*` | Menu and menu item labels |
| `action.*` | Action names (toolbar buttons, menu actions) |
| `dialog.<name>.title` | Dialog window titles |
| `dialog.<name>.*` | Other dialog text (labels, borders, tabs) |
| `error.*` | Error messages |
| `confirm.*` | Confirmation dialog messages |
| `tooltip.*` | Tooltip text |
| `label.*` | General UI labels not tied to a specific dialog |
| `about.*` | About dialog text |

### Template strings

Strings with embedded variables use `java.text.MessageFormat` patterns. Call `Strings.get()` with the additional arguments to format them.

#### Simple substitution

Use `{0}`, `{1}`, etc. for positional arguments:

```properties
error.file.open=Error opening {0}
confirm.save.modified={0} has been modified. Do you want to save it?
status.notes.selected={0} of {1} notes selected
```

```java
Strings.get(Strings.ERROR_FILE_OPEN, filename)
Strings.get(Strings.STATUS_NOTES_SELECTED, selected, total)
```

#### Number formatting

`MessageFormat` supports built-in format types:

```properties
export.progress=Exported {0,number,integer} of {1,number,integer} pages
file.size=File size: {0,number,#,###} bytes
```

#### Choice formatting

Use `{n,choice,...}` for pluralization and conditional text:

```properties
status.deleted={0,choice,0#No notes|1#1 note|1<{0} notes} deleted
confirm.close.unsaved=There {0,choice,0#are no unsaved files|1#is 1 unsaved file|1<are {0} unsaved files}. Close anyway?
```

```java
Strings.get(Strings.STATUS_DELETED, count)       // "No notes deleted", "1 note deleted", "5 notes deleted"
Strings.get(Strings.CONFIRM_CLOSE_UNSAVED, count) // "There are no unsaved files. Close anyway?"
```

The `choice` format syntax is `limit#text|limit#text|...` where:
- `limit#` — matches when value equals limit
- `limit<` — matches when value is greater than limit
- Limits must be in ascending order

#### Apostrophe escaping

`MessageFormat` uses single quotes as escape characters. In any template string (one accessed via `Strings.get(key, args...)`), literal apostrophes must be doubled:

```properties
# Wrong -- the apostrophe will swallow the next character
error.cant=Can't open file

# Correct
error.cant=Can''t open file
```

This only applies to strings used with `Strings.get(key, args...)`. Plain strings accessed via `Strings.get(key)` do not pass through `MessageFormat` and need no escaping.

### Multiline strings

Use `\n` for embedded newlines:

```properties
error.fatal=A fatal error has occurred.\nThe application must quit.
```

### HTML tooltips

Store with HTML markup included:

```properties
tooltip.tuplet=<html><strong>Tuplet</strong><br>Create or remove tuplet from the selection</html>
```

## Phase 1: Infrastructure (current scope)

### Step 1.1 — Create the properties file

Create `src/main/resources/songscribe/strings.properties` with a header comment and seed entries for testing (including template string examples):

```properties
# SongScribe user-facing strings
# This file is the single source of truth. The Strings.java constants class
# is generated from this file during the build.
#
# Key format: lowercase alphanumeric segments separated by dots.
#   Valid:   menu.file, dialog.about.title, error.file.open
#   Invalid: menu.File, menu.file-open, menu.file_open
#
# Template strings use java.text.MessageFormat syntax:
#   Simple:  error.file.open=Error opening {0}
#   Choice:  status.deleted={0,choice,0#No notes|1#1 note|1<{0} notes} deleted
#   Apostrophes in template strings must be doubled: Can''t open {0}

app.name=SongScribe
test.template.simple=Hello {0}
test.template.choice={0,choice,0#no items|1#one item|1<{0} items}
test.template.apostrophe=Can''t find {0}
```

### Step 1.2 — Create the Groovy generator script

Create `scripts/generate-strings.groovy`. The script:

1. Reads `src/main/resources/songscribe/strings.properties`
2. Validates each key against `[a-z][a-z0-9]*(\.[a-z][a-z0-9]*)*`
3. Converts each key to a constant name (uppercase, dots to underscores)
4. Checks for constant name collisions
5. Writes `target/generated-sources/songscribe/Strings.java`

On validation or collision failure, the script prints a clear error message and calls `System.exit(1)` to fail the build.

Generated class structure:

```java
// This is an auto generated code. DO NOT MODIFY!
package songscribe;

import java.text.MessageFormat;
import java.util.ResourceBundle;

public final class Strings {
    private static final ResourceBundle BUNDLE =
        ResourceBundle.getBundle("songscribe.strings");

    public static final String APP_NAME = "app.name";
    public static final String TEST_TEMPLATE_SIMPLE = "test.template.simple";
    // ... one constant per key, sorted alphabetically ...

    private Strings() {}

    public static String get(String key) {
        return BUNDLE.getString(key);
    }

    public static String get(String key, Object... args) {
        return MessageFormat.format(BUNDLE.getString(key), args);
    }
}
```

### Step 1.3 — Add Maven configuration to pom.xml

Two additions to pom.xml:

1. **New `<execution>` in the existing `gmavenplus-plugin`** — bound to `generate-sources`, references `scripts/generate-strings.groovy`.

2. **New `build-helper-maven-plugin`** — registers `target/generated-sources/` as a compile source root so Java and Kotlin compilers see `Strings.java`.

```xml
<!-- In gmavenplus-plugin <executions> -->
<execution>
    <id>generate-Strings-java</id>
    <phase>generate-sources</phase>
    <goals>
        <goal>execute</goal>
    </goals>
    <configuration>
        <scripts>
            <script>file:///${project.basedir}/scripts/generate-strings.groovy</script>
        </scripts>
    </configuration>
</execution>

<!-- New plugin -->
<plugin>
    <groupId>org.codehaus.mojo</groupId>
    <artifactId>build-helper-maven-plugin</artifactId>
    <version>3.6.0</version>
    <executions>
        <execution>
            <id>add-generated-sources</id>
            <phase>generate-sources</phase>
            <goals>
                <goal>add-source</goal>
            </goals>
            <configuration>
                <sources>
                    <source>${project.build.directory}/generated-sources</source>
                </sources>
            </configuration>
        </execution>
    </executions>
</plugin>
```

### Step 1.4 — Verify the build

- Run `./scripts/compile.sh` and confirm `Strings.java` is generated and compiles
- Verify IntelliJ indexes the generated sources after Maven reimport

### Step 1.5 — Add unit tests

Create `src/test/java/songscribe/StringsTest.java`:

**Key sync tests:**
- Uses reflection to read all `public static final String` fields from `Strings.class`
- Loads `strings.properties` via `ResourceBundle`
- Asserts every constant's value is a valid key in the bundle
- Asserts every key in the bundle has a corresponding constant
- Catches drift between the properties file and the generated class (e.g., stale build artifacts)

**Template string tests (using the seed entries from Step 1.1):**
- `get(TEST_TEMPLATE_SIMPLE, "world")` returns `"Hello world"`
- `get(TEST_TEMPLATE_CHOICE, 0)` returns `"no items"`, `get(..., 1)` returns `"one item"`, `get(..., 5)` returns `"5 items"`
- `get(TEST_TEMPLATE_APOSTROPHE, "file.txt")` returns `"Can't find file.txt"`

### Step 1.6 — Commit

Commit the infrastructure: properties file, Groovy script, pom.xml changes, and the test class.

## Scope exclusions

- **String extraction (Phase 2)** — deferred to follow-up branches
- **i18n / locale support** — future concern; ResourceBundle is i18n-ready but no locale bundles now
- **Hungarian strings in `MidiLister.java`** — separate i18n concern
- **Log messages** — internal, not user-facing
- **Debug/inspector strings** — developer-only UI, low priority
- **Programmatic identifiers** — strings used as map keys, property names, file extensions, etc. are not user-facing
- **Generator validation tests** — low-risk code (~40 lines), build failure is sufficient feedback

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| `MessageFormat` apostrophe escaping | Audit all strings containing `'` — must be doubled to `''` in template string values |
| Action names used as identifiers | Check for `getValue(Action.NAME)` comparisons before extracting |
| Build order — Kotlin compilation needs `Strings.java` | Groovy runs in `generate-sources` (before `process-sources` where Kotlin compiles), so this is safe |
| Large diff size | Incremental commits per category keep each change reviewable |
| Key collision | Generator detects and fails build with clear error naming both offending keys |
| Invalid key format | Generator validates against `[a-z][a-z0-9]*(\.[a-z][a-z0-9]*)*` and rejects non-conforming keys |
